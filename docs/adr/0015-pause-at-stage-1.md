# 0015: 段階1で一旦区切る。ファイル単位の理解スコアは、動機につながる指標にならなかった

- 日付: 2026-10-17
- ステータス: 採用

## 背景

ADR 0005 で、段階1は「ファイル単位の理解スコアと危険地帯が静的ページで見られる」ところまでに絞った。
広げるのは、スコアを実際に眺めて「使える指標だ」と確かめてからにする、と決めていた。

2026-10-17 に Phase 6（ADR 0014）まで作り終え、このリポジトリ自身で一周使った。

1. `danger .` で危険地帯を出し、`understanding.yml` に `core: [src/]` を設定した
2. 2位だった src/score.ts（score 0.29、人間のコミット0件）を、説明を読んで理解した
3. `ack` で記録すると、src/score.ts は危険度 0.39 から 0 になり、上位10件から外れた
4. GitHub Pages への公開まで確かめた

ツールは設計どおりに動いた。それでも、使った本人（作者）の感想は「ツールそのものが微妙」だった。

## 決定

段階1はここで一旦区切る。段階1の問い「理解スコアは使える指標か」への答えは、今のところ「使えるとは言えない」とする。

- コードは今の形のまま残す。公開ページも、手動実行で更新できる状態のまま残す（ADR 0014）
- 段階1の残り（Phase 3 の PR レビュー、PR 単位の ack、λ と併走倍率の見直し）には着手しない
- 段階2以降（Action 化、App 化など）にも進まない。ADR 0005 の条件を満たしていないため

### 理由（一周使ったフィードバック）

作者が挙げた理由は2つ。

- **ファイル単位で追うのは、実装の側に寄りすぎている。** モデル（何をどう分けて考えているか）と実装のうち、ファイルは実装の単位である。ファイルを1つずつ理解することに、そもそも意味があるのか疑わしい
- **脆弱性診断のスコアに近い。** スコアが悪いと示されても、それを理由に「じゃあ理解しよう」と腰を上げる動機が薄い。減点を見せられるだけでは、やる気にならない

使っている途中で見えたことも、この2つを裏づけている。

- 全部を AI と書く一人開発では、ほぼすべてのファイルのスコアが低くなる。危険度の順位はほぼ変更頻度で決まり、上位に来るのは言われなくても分かっているファイル（このリポジトリでは src/index.ts）だった
- 理解が起きたのは、説明を読んだときだった。スコアは、そのあと `ack` を押したことに従って動いただけで、理解そのものは測っていない
- 説明で効いたのは、ファイルの中身ではなく形（どこで何が交わるか、依存の向き）だった。このツールは形を知らない
- tekito-uranai では、多くの変更が通るハブ（App.tsx など）が、ファイル単位の ack では永久に上位に残ることを確かめていた（2026-10-16）

## 検討した選択肢

- 段階1を続けて、スコアの式（λ、併走倍率、AI 側の `min(1, r)`）を調整する — 式を直しても「ファイル単位」と「減点で動機づける」という2つの問題は残る
- 主役をスコアから「次に何を読むか、その材料」に移す — スコアの見せ方は変わるが、単位はファイルのままである。続けるなら、どの単位で何を読ませるかから考え直す必要がある
- vision.md の2段目（依存の形、宣言された形と実際の形のズレ）に進む — 形を扱うので、1つ目の理由に応えられる可能性がある。ただし、ズレをスコアとして見せるなら2つ目の理由（動機）は残る。今はまだ決めない
- このリポジトリを閉じる（アーカイブする） — 「思想＋動くもの＋やってみた結果」をセットで出すという vision.md の位置づけからすると、うまくいかなかった結果も残す価値がある

## 結果

- 段階1は「動くもの」と「やってみた結果」がそろった状態で止まる。この ADR がその結果の記録になる
- 再開するときは、次の2つに答えられる案から考える
  - 何の単位を追うのか。ファイルより、モデルや形に近い単位にできるか
  - 人が自分から理解しに行く動機をどう作るか。減点の提示以外の形はあるか
- `docs/plan.md` の段階1のゴール（毎日自動更新される静的ページ）と Phase 6 の完了条件（毎朝ページが自動で更新される）は、ADR 0014 で手動実行に変えたため満たしていない。区切るので、満たさないままにする
