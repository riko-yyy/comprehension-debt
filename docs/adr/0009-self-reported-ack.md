# 0009: 一人開発では、自己申告の ack を理解イベントにする

- 日付: 2026-10-15
- ステータス: 採用

## 背景

計画の Phase 3 では、PR の実質的なレビューを理解イベントにする予定だった。
しかし手元の5つのリポジトリ（PR は合計57件）には、人間のレビューが1件もなかった。コメントは Vercel の bot だけだった。
一人で開発しているため、レビューという行為がそもそも起きない。このまま Phase 3 を作っても、スコアはまったく変わらない。

一方で ADR 0007 のスコアでは、人間が理解度を上げる手段が「自分でコードを変更する」ことしかない。
読んで理解しただけでは、スコアに反映されない。

## 決定

- `npm run cli -- ack <repo-path> <path>...` で「このファイル／ディレクトリは読んで理解した」と記録する
- 記録は対象リポジトリの `.understanding/acks.jsonl` に、1行1件の JSON で追記する
  - `{"path":"src/App.tsx","date":"2026-10-15T22:10:00+09:00","by":"riko_yyy"}`
  - `path` がディレクトリなら、その中のファイルすべてに当てはまる
  - `by` は git の `user.name`。段階1では使わないが、vision.md の組織層（誰が何を理解しているか）を見るときに要る。後から足すと過去の記録に入らないので、最初から入れる
  - 日時は、コミットの日時と同じくタイムゾーン付きのローカル時刻
- スコアの計算では、履歴を再生するときに ack をその日時の理解イベントとして差し込み、理解度を 1 に戻す。
  人間の変更（変更した割合だけ戻す）と違い、ファイル全体を読んだという申告なので満点にする
- 打ち間違いを防ぐため、HEAD にないパスの ack はエラーにする
- `.understanding/` は既定でスコアの対象から除外する（ADR 0008 の既定パターンに追加）
- `score` の表の「最後に人間」の列を「最後の理解」に変え、人間の変更と ack の新しいほうの日付を出す

## 検討した選択肢

- 計画どおり PR レビューを理解イベントにする — 一人開発ではデータがない。段階2以降でチームに配るときに作る
- 記録をこのツールのリポジトリに、対象リポジトリごとに置く — 対象リポジトリにコミットせずに済むが、`understanding.yml` と別の場所になる。Phase 6 で対象リポジトリを clone したときに記録が付いてこない
- ack を人間の変更と同じく部分的な回復にする — 何割理解したかを申告させるのは手間で、根拠もない
- クイズに答えられたら ack する — 申告に頼らない良い方法だが、一問レビュー bot（段階1の後）で考える

## 結果

一人開発でも、読んで理解したことをスコアに反映できる。
自己申告なのでごまかせるが、段階1は自分用なので問題にしない（ごまかす動機がない）。
ack を記録したら対象リポジトリでコミットする手間がある。
ack の後にファイルがリネームされると、古いパスの ack は新しいパスに当てはまらない。困ったら、リネームを追いかけるか、もう一度 ack する。
ack の有効期限（時間が経つと忘れる）は入れていない。vision.md の時系列の減衰と合わせて、後で考える。
