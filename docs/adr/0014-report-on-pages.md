# 0014: GitHub Actions でレポートを作り、GitHub Pages に公開する（まずは手動実行だけ）

- 日付: 2026-10-17
- ステータス: 採用

## 背景

Phase 6 では、Phase 5 のレポート（ADR 0012）を、手元で `report` を打たなくても見られるようにする。
λ=1、併走倍率=0.5 は暫定（ADR 0011）で、スコアを眺めながら上位10件の並び順を見直したい。
そのためには、レポートが決まった場所に並んでいる必要がある。

当初の設計は「毎朝6時（JST）の定期実行、対象は手元の公開リポジトリ5つ」だった。
実装したあと、まずは手動実行だけ、対象はこのリポジトリだけにして様子を見ることにした。

## 決定

- 対象はリポジトリのルートの `targets.yml` に並べる。`name`（公開先のディレクトリ名）と `repo`（`owner/name`）の組。今はこのリポジトリだけ
- `npm run site` が、対象を一時ディレクトリに全履歴つきで `git clone` し、`report --out site/<name>` を実行して、最後に一覧ページ `site/index.html` を書く
- `.github/workflows/report.yml` は、Actions の画面から手動で実行したときだけ `npm run site` を動かし、`site/` を GitHub Pages に公開する。定期実行（`schedule`）は付けない
- 対象は公開リポジトリだけにする。clone にトークンが要らない
- 対象の `understanding.yml` と `.understanding/acks.jsonl` は、その対象のリポジトリにあるものが使われる
- 1つでも失敗したら（clone できない、`report` が落ちる）、その回は公開しない。前回のページが残る

作らないもの: 定期実行、日ごとのスナップショット（履歴の比較）、通知、PR コメント、非公開リポジトリの対象化。

## 検討した選択肢

- 毎朝の定期実行 — 当初の設計。何を見たいかが固まる前に毎日更新しても、眺める習慣がなければ意味がない。手動で何度か回して、見る価値を確かめてから足す
- 手元の公開リポジトリ5つを最初から対象にする — 当初の設計。まず1つで公開の流れを確かめる。増やすのは `targets.yml` に1組足すだけ
- `actions/checkout` で対象を取得する — 既定で最新1コミットしか取らない（ADR 0007 の既知の注意点）。`fetch-depth: 0` を毎回書き忘れないようにするより、`git clone` で全履歴を取るほうが確実。手元でも同じ `npm run site` で確かめられる
- 対象ごとにジョブを分ける（matrix） — 一覧ページを書くために結果を1か所に集め直す必要がある。対象が少ないうちは、1つのジョブで順に回せば足りる
- 失敗した対象だけ飛ばして公開する — 一覧から黙って消えると気づけない。全部止めて Actions の失敗として見えるほうがよい
- 非公開リポジトリも対象にする — 読み取り用トークンの管理が要る。公開ページに非公開リポジトリのファイルパスと「理解できていない場所」が載ってしまう

## 結果

- 手動で実行すると、`https://riko-yyy.github.io/comprehension-debt/` に最新のレポートが出る
- 公開ページには、対象リポジトリのファイルパスと、理解できていない場所が誰でも見える形で載る。対象が公開リポジトリなので、コード自体はもともと見える
- 危険度の「変更頻度」は実行した日から90日をさかのぼって数えるので、コミットがなくても実行する日によって値が変わる
- 定期実行を足すなら `on:` に `schedule` を足す（GitHub の cron は UTC）。そのときは、公開リポジトリで60日間コミットがないと定期実行が止まることに注意する
- 有効にするには、人間が Settings → Pages の Source を「GitHub Actions」にする
