# 0007: 理解スコアは履歴を再生して、変更の割合で上げ下げする

- 日付: 2026-10-15
- ステータス: 採用

## 背景

Phase 2 では、ファイルごとに「人間がどれだけ理解しているか」を 0〜1 のスコアにする。
計画（plan.md）では「最後に人間がそのファイルを変更した時点以降の AI 変更行数」で計算する案だった。
しかしこの案では、人間が1行直しただけでスコアが満点に戻ってしまう。

## 決定

ファイルの変更履歴を古い順に再生し、変更のたびに理解度 `u` を更新する。

- 初期値は `u = 1`（まだ存在しないファイルには、理解すべきものがない）
- 変更の割合 `r = 変更行数（追加 + 削除）/ max(変更前の行数, 変更後の行数, 1)`
- 人間の変更: `u ← u + (1 - u) × min(1, r)`（変更した割合だけ、理解していない部分を埋める）
- AI の変更: `u ← u × exp(-λ × w × r)`（w は自律 = 1、併走 = `pairWeight`）
- 行数は履歴の追加・削除の累積から推定する（git blame は使わない）

既定値は `λ = 1`、`pairWeight = 0.5`。`--lambda` と `--pair` で変えられる。
この既定値だと、AI が単独で新規作成したファイルは 0.37、併走で新規作成したファイルは 0.61 から始まる。

## 検討した選択肢

- 最後の人間の変更以降の AI 変更行数で計算する（計画の案） — 1行の修正で満点に戻る
- git blame で、今残っている行を誰が書いたか数える — 書き換えや削除の量が見えない。重い
- 人間の変更も行数比で減衰の逆をかける（`u ← 1 - (1 - u) × exp(-r)`） — 上げ下げの式が非対称で直感に合わせにくい

## 結果

人間の小さな修正は小さく、大きな書き直しは大きく理解度を戻す。
`design-doc-repo`・`ddd-dojo`・`aws-dotnet-lab`・`tekito-uranai` で試すと、AI のコミットはほぼ全部が併走だった。
併走しかないリポジトリでは、`λ` と `pairWeight` を変えてもスコアの並び順は変わらず、値の大きさだけが変わる。
そのため、この2つの値が効くのは「どこから危険とみなすか」の閾値（Phase 4）と、自律の変更が混ざったときになる。
値の確定は、Phase 4 で危険地帯を眺めてから行う。

自動生成ファイル（`package-lock.json` など）や SVG もスコアの低い側に並ぶ。除外ルールは Phase 4 の前に別 ADR で決める。

### 既知の注意点

- 行数は履歴の最初からの積み上げで推定している。浅い clone など、履歴が途中から始まるとずれる（Phase 6 では `fetch-depth: 0` が必須）
- numstat では1行の書き換えが「1行削除 + 1行追加」になり、変更行数は2と数えられる。人間と AI の両方に同じように効くので並び順への影響は小さいが、λ の値の意味を考えるときの前提になる
- 人間の変更は回復量に上限（割合 1）があるが、AI の変更の割合には上限がない。AI がファイルを全部書き換えると割合が 2 近くになり、新規作成（割合 1）より理解が下がる。これは意図したものではない。直すなら AI 側も `min(1, r)` にそろえる（書き直されたファイルは、新規作成と同じくらい未知とみなす）。Phase 4 で閾値を決めるときに一緒に判断する
